## 五、今日一问（成稿）

**问：回滚演练花了多久？真出事你敢不敢用这套流程？**

**答：** 花得起的时长——发布 ≤8 分钟、回退 ≤3 分钟、恢复 ≤1 分钟，全程约 13 分钟，而且这还是边演练边截图的节奏。真出事敢不敢用：**静态托管这条路径敢**，理由有四条——① 动作和日常发布一模一样（同样的 5 步上传），靠肌肉记忆，不临场学新东西；② 上一版产物事先快照（`releases/v0.1/`）+ Git 标签锚点（`v0.1`），拿什么传、为什么是它，不用现场判断；③ 平台对 HTML 是 `no-store` 不吃缓存，传完即生效，不存在「回退了但用户看到旧的」的窗口；④ 验证有硬判据（哈希指纹 + 页头版本标识），不靠「看着好像好了」。**两条如实说不敢的**：云函数回退和数据恢复今天刻意没练（今日不做，手册 §3/§4 备查），真出那两种事得现场对照手册走，速度没验证过——这是下回欠账，不是这次吹牛。

## 六、平台事实（当天核实，已写进手册）

- CloudBase 静态托管**没有**「一键回退到历史版本」功能；回退 = 重传上一版产物覆盖（官方文档明示覆盖语义）。
- `index.html` 响应头 `cache-control: no-store`——上传即生效；css/js 靠 `?v=` 版本号破缓存。
- `Last-Modified` 响应头可当免费时间戳证据。
- `git archive` 默认会被 `core.autocrlf` 换行转换坑到；正确的产物重建命令是
  `git -c core.autocrlf=false archive <tag>`（与当初上传的产物逐字节一致）。
