# 回滚手册 · Rollback Manual

适用版本：v1.0 起（2026-10-12 建立）
维护约定：**每次发布新版本后回读一遍本文**，路径变了就改；演练一次就在 §2.4 记一行。

> 回滚的含义：**把线上指回一个已经存在的版本，而不是现场改代码。**
> 所以回滚的前提是"历史可回退"——每个发布版本都有标签（tag）和产物快照。
> 这两样东西平时看着没用，出事那一刻它们就是全部。

---

## 0. 什么情况必须回滚（判断表）

先判断要不要回滚，再动手。**回滚有成本**（丢掉新版本的全部改动），所以不是所有毛病都值得回。

| 症状 | 要不要回滚 | 理由与动作 |
|---|---|---|
| 页面白屏 / 打不开 | **必须回滚** | 用户完全用不了，网站等于不存在。退回上一版，恢复服务后再慢慢查 |
| 卡片内容张冠李戴（A 菜显示 B 菜的故事） | **必须回滚** | 错误的文化资料比没有资料更糟——这个产品的底线是"可信" |
| 接口连续 5xx（刷新几次都失败） | **必须回滚**（回退云函数） | 页面只剩本地兜底数据，13 道菜变 12 道、公网数据全丢；先退接口再查 |
| 密钥 / 管理口令泄露 | **必须回滚 + 换密钥** | 安全问题。先撤掉泄露的凭据、换新密钥，再考虑功能层面 |
| 控制台有报错但页面功能正常 | **不用回滚** | 记下来、排进下一次修复。为一条控制台红字回退整个版本，得不偿失 |
| 样式小毛病（错位、颜色、字号） | **不用回滚** | 不影响可用性与可信度，正常修就行 |
| 某道菜的数据写错了 | **不用回滚** | 单点数据问题，用 PATCH 接口改那一条即可，回滚是杀鸡用牛刀 |
| 数据库里数据被误删/写坏 | **恢复数据**（不回滚前端） | 前端没坏，回滚它没用。走 §4 数据恢复 |
| 新版本只是"没达到预期"，但没坏 | **不用回滚** | 没有用户受损就不付回滚的代价；下一版改进 |

一句话版：**用户用不了、内容不可信、凭据泄露，这三类必须回；其余记下来修。**

## 1. 三条回退路径总览

| 层 | 出问题的东西 | 回退方式 | 状态 |
|---|---|---|---|
| 静态托管 | 页面 / 样式 / 前端数据文件 | 重传上一版产物覆盖线上（§2） | ✅ Day 26 已实测 |
| 云函数 | 接口逻辑（`db.js` / `index.js`） | 控制台重贴上一版代码（§3） | 备查，未实操 |
| 数据 | 库里的数据被写坏 | 重灌建表与种子脚本（§4） | 备查，未实操 |

三条路径互相独立：前端坏了不用动库，接口坏了不用动前端，数据坏了前端和代码都不用动。
**先判断坏在哪一层，再走对应的路径**——最忌讳三层一起动，那等于把现场毁了。

## 2. 静态托管回退（已实操，首选路径）

### 2.1 回退前提：上一版的产物在哪

按优先级：

1. **`releases/<标签>/`** —— 发布时从 `deploy/` 存出的快照（首选，拿来就能传）。
2. **用 git 标签重建** —— 快照没了也能造回来（本仓库 28 个提交、0 个合并、线性历史，任何一天的版本都在）：

   ```
   git -c core.autocrlf=false archive v0.1 -o 上一版.tar
   ```
   解开后取 `index.html` + `assets/` + `css/` + `js/` + `data/` 即为可上传产物。

   ⚠️ **坑（2026-10-12 实测）**：直接 `git archive <标签>` **不加** `-c core.autocrlf=false`，
   导出的文件会被按 `core.autocrlf=true` 转成 CRLF，与当初上传的产物**哈希不一致**
   （本仓库工作区是 LF）。浏览器渲染没区别，但任何 MD5 比对都会对不上。
   **重建一律带 `-c core.autocrlf=false`。**

3. **都没有**（标签没打、快照没了）—— 那就只能从 git 历史里找最接近的提交重建。
   这就是为什么**每次发布必须打标签**。

### 2.2 回退步骤（对照发布步骤，一模一样）

控制台路径：CloudBase 控制台 → 环境 `vibecodingstudy-d1f1el6a03d5aad8` → 静态网站托管 → 文件管理

| 步 | 操作 | 选什么 |
|---|---|---|
| 0 | **看一眼时钟，记下「时:分：秒」**（回退也要记时，耗时数据靠这个） | —— |
| 1 | 「上传文件」 | `releases\v0.1\index.html` |
| 2 | 「上传文件夹」 | `releases\v0.1\css` |
| 3 | 「上传文件夹」 | `releases\v0.1\js` |
| 4 | 「上传文件夹」 | `releases\v0.1\data` |
| 5 | 「上传文件夹」 | `releases\v0.1\assets` |

⚠️ 选的是 `css` / `js` / `data` / `assets` **文件夹本身**，不是进去挑文件。
⚠️ 上传会**覆盖**线上同名文件（官方文档明示的语义）——这正是回退的机制。
⚠️ `assets/` 目录容易漏（它是 Day 24 才新增的顶层目录）。

### 2.3 回退后怎么验证（不许凭肉眼说"好了"）

1. **指纹比对**：抓线上 `index.html` 与 `css/style.css` 的 SHA-256，与快照逐字节比
   （本仓库用 `deploy-mirror` 同款脚本；哈希一致才算回退成功）。
2. **肉眼判据**：v1.0 的页头版本标识（`v1.0` 胶囊标签）**消失**。
3. **跑发布前检查**：`node skills/pre-release-check/scripts/check-release.mjs --browser`
   —— 0 阻断才叫恢复。此时 `deploy-mirror` 会提示 deploy/ 与源码不一致，**这是预期内的**
   （线上是旧版、源码是新版），演练结束恢复 v1.0 后自然消失。

### 2.4 实测记录（2026-10-12 演练已填）

计时口径：以下「确认时刻」= 操作人亲眼在公网页面上看到预期版本的时刻；
另有一路独立证据 = 静态托管响应头的 `Last-Modified`（服务器时间，不受肉眼影响）。

| 日期 | 方向 | 公网确认时刻 | 耗时（按确认时刻差） | 操作人 |
|---|---|---|---|---|
| 2026-10-12 | 发布 v1.0 | 20:43（截图①） | ≤ 8 分钟（20:34:39 起点指纹 → 20:43） | Amity |
| 2026-10-12 | 回退 v0.1 | 20:46（截图③） | ≤ 3 分钟（20:43 → 20:46） | Amity |
| 2026-10-12 | 恢复 v1.0 | 20:46:45（服务器 `Last-Modified`，20:48 起连续 8 次探测稳定） | ≤ 1 分钟（20:46 → 20:46:45） | Amity |

**实测补两条平台事实**（当天核实）：

- 静态托管对 `index.html` 的响应是 `cache-control: no-store, no-cache`——**HTML 不吃 CDN 缓存，
  上传完即生效**（上面 ≤1 分钟的恢复速度就是证据）。`css/js` 带 `?v=` 版本号，靠升版本号破缓存。
  所以本项目的「回退生效慢」风险基本不存在，真正要等的只是自己上传的 1–2 分钟。
- `Last-Modified` 响应头就是**免费的时间戳证据**：争测「到底哪版在线上」时，它比截图更硬
  （服务器时间 + 文件内容哈希，两头都对得上才算数）。

> 记录粗糙处如实记：回退一轮的「开始上传时刻」没记（只记了确认时刻），所以上表耗时是上界
> （≤ 而非 =）。下次演练起传前先看一眼时钟——已写进 §2.2 步骤 0。

## 3. 云函数回退（备查，今日未实操）

现状：云函数 `scf-nodejs-helloworld-yfxb` 在控制台**只有一份在线代码，没有历史版本**，
所以它的回退同样是"重贴上一版"。

1. **取上一版代码**（不要凭记忆手敲）：
   ```
   git show v0.1:cloudfunctions/api/index.js > 上一版-index.js
   git show v0.1:cloudfunctions/api/db.js   > 上一版-db.js
   ```
2. 控制台 → 云函数 → `scf-nodejs-helloworld-yfxb` → 函数详情 → 文件树点开 `index.js`
   → **Ctrl+A 全选删掉** → 粘贴上一版全文 → 部署。`db.js` 同样操作。
3. **环境变量不用动**（`CLOUDBASE_API_KEY`、`ADMIN_TOKEN` 是函数级配置，重贴代码不影响）。

⚠️ 三个实测过的坑：
- 两个文件**必须都重贴**，漏一个 → `/api/*` 全体 `FUNCTIONS_INVOCATION_FAILED`。
- `/api/health` 返回 200 **不能**当主函数存活判据 —— 它由另一个独立云函数响应。
  主函数判据用 `/api/dishes` 这类业务端点。
- 粘贴不完整不会有任何报错提示，只有接口全挂这一个症状。贴完必须实跑验证。

## 4. 数据恢复（备查，今日未实操）

库：CloudBase PostgreSQL（环境 `vibecodingstudy-d1f1el6a03d5aad8`），6 张表。
入口：`https://tcb.cloud.tencent.com/dev?envId=<环境ID>#/db/postgres` → 左侧「SQL 编辑器」。

1. **表结构坏了** → 重灌 `db/schema.exec.sql`（建表，含 `DROP TABLE IF EXISTS`，会清数据）。
2. **数据坏了/被误删** → 依次重灌：
   - `db/schema.exec.sql`（重建表）
   - `db/seed.exec.sql`（灌种子）
   - `db/grants-write.sql` + `db/grants.sql`（重新授权，**漏了这步接口会 403**）
3. **只错了几道菜** → 不必重灌，用 `PATCH /api/dishes/{id}` 改那几条（需 `X-Admin-Token`）。

⚠️ **要粘的是 `db/*.exec.sql`（零注释版）**，不是 `schema.sql` / `seed.sql`
—— 控制台按分号切语句，带注释的版本里 13 行注释含分号，会被当成真语句执行，直接报错。

⚠️ 目前 DELETE 是**真删**（软删除 `is_deleted` 是 Day 22 记下的待办，未做）。
被删的菜没有软删除兜底，只能靠重灌种子数据找回；`data/dishes.json` 是数据的源头副本。

## 5. 平台能力查证（2026-10-12，官方文档）

写手册前查证过，免得凭印象：

- CloudBase 静态托管官方文档列出三种部署方式：上传代码包 / 控制台上传文件与文件夹 / CLI；
  并明示 **「上传会覆盖同名文件」**。
- **文档未提供"一键回退到历史版本"的能力**（那是"云托管"的功能，别混淆）。
- CLI（`@cloudbase/cli`）提供的能力值得知道：
  - `tcb hosting deploy <目录> -e <环境ID> --safe` —— 发布前把远端文件备份到
    `.cloudbase-backup/<时间戳>/`，上传或校验失败时**自动回滚**；
  - `--verify` —— 发布后比对远端与本地产物的大小与 MD5；
  - `tcb hosting list / detail / delete` —— 查看远端文件清单与服务状态。
- **结论**：本项目的静态托管回退 = **重传上一版产物覆盖**（本文 §2）。
  `--safe` 是它的自动化加强版，将来若装 CLI 可作升级项（今日不做，避免引入新依赖）。

## 6. 回滚之后必做的三件事

1. **跑发布前检查**，确认 0 阻断（别把"看起来恢复了"当成"恢复了"）。
2. **在 §2.4 记一行**：什么问题、回退到哪个版本、耗时多少。耗时是这套流程唯一的改进依据。
3. **问题另立清单**，修好并重新走完发布前检查后，才允许再次发布 ——
   别让"回滚"变成"把问题藏起来"。
