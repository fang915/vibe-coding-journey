# 改写提示词与复盘（验收项：提示词理解与改写，20 分）

> 评分表要求「3 条以上实际改写提示词和复盘」。本文收 4 条：Day 18 / Day 19 两条是当时留档的**原文**（也写在 `docs/demo-outline.md` §③）；Day 24 / Day 25 两条是按当日记录复原的**大意**（原话没逐字留档，复原处已标注）。

## ① Day 18｜写接口：课程示例是「收藏」，项目口径是「策展端新增菜」（原文留档）

**原始提示（照课程清单原文）**：

> 「实现 POST 接口，防止重复提交，部署并完成一次真实写入 + 读回验证。课程示例是 `POST /api/favorites`（收藏）。」

**为什么不能照抄**（三条硬冲突）：

| 冲突 | 出处 |
|---|---|
| 本项目没有用户体系，也不收集用户数据 | `PRD.md` §9 非目标第 4 条 |
| 本期不该有面向用户的写接口 | `api-contract.md` §6「本期没有任何写接口（不是漏了）」 |
| 前端没有收藏按钮，无登录换设备就丢 | 全项目搜「收藏 / favorite」零命中 |

**改写后（当天实际执行）**：

> 「给**策展端**加一条新增菜接口 `POST /api/dishes`：① 用请求头口令 `X-Admin-Token` 区分「是不是我们自己发的」，口令放环境变量；② 防重复提交不靠 JS 先查再插，直接让数据库主键挡（撞 `pk_dishes` 就报 409）；③ 缺必填字段一次报全、提示用中文；④ 返回读回库里的那一行，不是回显请求体；⑤ 不改动已验收的四条 GET。」

**复盘**：教学点（缺字段 400 / 重复被拒 409 / 库多一行）全部保住，但不违背 PRD 非目标、不用新建表、前端零改动。**教训：课程示例是教具，不是需求；先对着自己项目的 PRD 过一遍冲突，再动手。**

## ② Day 19｜重构：「重构一下代码」太空，改成「只搬家、不装修」（原文留档）

**原始提示**：「重构一下代码」（照课程清单的泛化要求）。

**为什么不能照抄**：范围没有边界。重构最容易把已经验收过的行为改坏，而当天没有任何新功能要加。

**改写后（当天实际执行）**：

> 「**只搬家、不装修**：把『和网关打交道』整节（约 190 行：`restGet` / `restInsert` / `gatewayError` / `parseTotal` + 网关常量）原样移到 `cloudfunctions/api/db.js`，`index.js` 只留 `require('./db.js')`；**逻辑一行不改、接口路径与字段名一个不动**；改完必须跑通离线 73 项自测。」

**复盘**：重构的安全感来自「可对照的基线」（73 项自测 + 路径字段不动），不来自「我小心一点」。**教训：把泛化动词（重构 / 优化 / 美化）翻译成可验收的边界条件，AI 才有护栏。**

## ③ Day 24｜图片修复：「把图修好」→「不赌外网，先保证页面永远不空」（按当日记录复原大意）

**原始需求（大意）**：修复 5 张菜品图加载失败、卡片显示粉色空块的问题。

**为什么不能照抄**：查下来是 `upload.wikimedia.org` 在用户网络环境不可达——「修图」等于赌一个自己控制不了的境外图床，修好了也不稳定。

**改写后（实际执行的方案，大意）**：

> 「不追境外图床：① 加 `IMAGE_SOURCE` 图源开关，默认本地占位；② 自绘 `placeholder-dish.svg` 占位图 + `favicon.svg`；③ 每张图挂 `bindImageFallback` 兜底（`data-fallback` 防循环）；④ 升版本号并同步部署镜像。真实美食图源记入 v1.1 待办。」

**复盘**：当天最大的坑不是图，是新写的 SVG 注释里含 `--`，浏览器**静默拒渲染**、控制台零报错——最后靠无头浏览器探针比对两版数字才定位。**教训：修复类需求要把「什么情况下算修好」说成可测的数字（图床请求 6→0、缩略图 0/5→5/5），否则感觉修好了不算数。**

## ④ Day 25｜检查工具：「做个发布前检查」→「16 条判据 + 四级状态 + 故意弄坏验证」（按当日记录复原大意）

**原始需求（大意）**：把发布前的手工检查做成可复用的 Skill。

**附加要求（当天明确提出）**：故意弄坏一项，验证检查工具真的会红，不许虚报通过。

**为什么不能照抄**：「做个检查」没有判据就没有可信度；而且没亲眼见过它失败的检查工具，等于没检查。

**改写后（实际执行的方案，大意）**：

> 「① 判据 16 条分四层（仓库卫生 / 密钥 / 工程 / 公网渲染），纯 Node 零依赖；② 状态分 FAIL / WARN / PASS / SKIP，SKIP 单独计数不冒充通过，有 FAIL 退出码 1；③ 每条判据先校准——故意注入三个故障（硬编码口令 / 改内容不升版号 / 镜像漏同步），全被抓出、还原后全绿才算数。」

**复盘**：第一版实跑 2 个 FAIL **全是误报**（判据写得不对，不是站点不对），校准了三次才定稿。**教训：检查工具本身也要被检查；「它报红 = 站点坏了」和「它报绿 = 站点好了」是两句话，后者只有在它抓到过真故障之后才能说。**
